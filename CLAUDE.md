# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`ai` is a minimal, agentic CLI that pipes stdin/prompts into an OpenAI-compatible LLM endpoint and runs an autonomous tool-calling loop in the terminal. The binary and command are `ai`. It is a fork of [chethanreddy1/infer](https://github.com/chethanreddy1/infer).

## Build, install, run

```bash
make                           # build ai (ai.c ai_frontend.c ai_toolclient.c ai_session.c ai_terminal.c ai_git.c cJSON.c) + libremote_harness.so; needs libcurl, libssl
make ci                        # clean rebuild with -Werror + C harness test (what CI runs); keep the C sources warning-free
./install.sh                   # build + install to ~/.local/bin, packages to ~/.local/share/ai/lib, sync skills (no sudo)
./install.sh llama             # also set up local llama.cpp server + model download
./install.sh snap              # also detect and configure a running AI snap (qwen3-6/gemma4)
```

`install.sh` copies the lib packages (`aitools`, `zulip_bridge`, `agent`, `trader` → `~/.local/share/ai/lib`, each staged and swapped in by rename) BEFORE it replaces the binary and the shims in `~/.local/bin`, so a process started mid-install never pairs a new shim with an old/missing package. It does NOT run `ai_mcp.py state-migrate` (the legacy-file migration runs lazily on the first state-store connect) and never restarts anything: restart a running Zulip bridge yourself afterwards (`systemctl --user restart zulip-ai-bridge`); the trader daemon runs a deployed release (`trader/deploy.sh`), not the installed copy.

Backend and model deployment are managed by `ai-backend` (single tool, installed to `~/.local/bin/ai-backend`, aliased as `ai-model` and `ai-use`). Active config lives in `~/.local/share/ai/env`.
```bash
ai-backend status                     # show active backend, model, and server status
ai-backend use <hf_uri|path|preset>   # download (if HF URI) and switch active model
                                      # e.g.: ai-backend use hf://AtomicChat/Ling-3.0-flash-GGUF/AD-IQ3_M/Ling-3.0-flash-AD-IQ3_M-00001-of-00002.gguf
ai-backend list                       # list downloaded GGUF models
ai-backend auto                       # switch to whatever is currently running
ai-backend ctx <size|auto>            # set or clear explicit context window
ai-backend gpu-layers <n|auto>        # set GPU offload layers
ai-backend serve                      # run llama-server with auto context sizing (used by systemd)
ai-backend profile [show|apply|off]   # per-model sampling profile (also applied by `use`)
ai-backend spec dflash <draft.gguf>   # DFlash speculative decoding (LLAMA_MTP=1, LLAMA_SPEC_TYPE=draft-dflash,
                                      # LLAMA_MTP_DRAFT_PATH); `ai-backend draft <*DFlash*.gguf>` does the same
```

Speculative drafts (`find_mtp_draft`): an explicit `LLAMA_MTP_DRAFT_PATH` (or a non-dspark `LLAMA_DRAFT_MODEL_PATH` named *mtp*/*dflash*, or any under `draft-dflash`, for a non-DeepSeek model) ALWAYS wins -- except a *DFlash* file under `draft-mtp`, which is ignored with a warning; if it is missing, nothing is auto-picked (warning). `mtp on` / `mtp <n>` drop a DFlash `LLAMA_MTP_DRAFT_PATH`; `use` drops a draft path whose name prefix differs from the new model's. Auto-detection only picks a sibling (model dir, then `MODEL_DIR`) with the model-name prefix, smaller than 1/3 of the main model (a full `...-mtp.gguf` model with built-in MTP heads is not a draft) and named for the spec type: `mtp` for `draft-mtp`, `dflash` for `draft-dflash` (an MTP file is never used for DFlash: llama-server aborts "DFlash model has no target_layer_ids"). Prompt cache: `LLAMA_CACHE_RAM` (MiB, passed as `--cache-ram`; -1 unlimited, 0 off) always wins; unset, ctx >= 65536 gets `--cache-ram 4096` (llama.cpp's default 8192 got llama-server SIGKILLed while evicting a 3.6 GB entry at ~94K tokens on Qwen3.8-27B), smaller contexts keep llama.cpp's default. Tests: `tests/test_ai_backend_draft_cache.py`.

On-demand serving: `services/llama-proxy.py` (installed by `install.sh` to `~/.local/bin/llama-proxy.py`, run by the user unit `llama-proxy.service`, which install.sh never restarts) listens on :8080, starts `llama-server.service` (`ai-backend serve --foreground`, backend :8081) on the first inference request, waits for its `/health` and forwards (SSE as it arrives). If the unit fails (VRAM preflight abort) or is not healthy within `LLAMA_PROXY_START_TIMEOUT` (default 180 s) the request gets 503 `{"error": {"type": "backend_unavailable", "message": <reason from this attempt's journal>, "log": [...]}}`; a failure is cached `LLAMA_PROXY_FAIL_CACHE` s (default 10). `/health` never starts the backend: `{"status":"ok","proxy":"ok","backend":"down|starting|ready|failed","reason":...}` (HTTP 200). A client disconnect closes the upstream socket (llama-server cancels). Ports/unit/timeouts: `LLAMA_PROXY_HOST/PORT/BACKEND_HOST/BACKEND_PORT/SERVICE/UPSTREAM_TIMEOUT` (upstream: no byte for 900 s by default; prompt_progress chunks are forwarded as they arrive). `ai-backend status` reads this body: `State: PROXY UP :8080 · backend <state>[: reason]`, RUNNING only when the backend is ready. Tests: `tests/test_llama_proxy.py` (private ports, fake `systemctl`/`journalctl`/backend).

Tests (pytest, `python3 -m pytest tests/ -q`, ~5 min, offline):

- Engines: tests taking the `engine` fixture (`tests/conftest.py`) run once per engine (`INFER_ENGINE=c|py`, `INFER_ENGINE_STRICT=1`). Every other test runs the binary's default (py): the root `conftest.py` drops any inherited `INFER_ENGINE` and sets `INFER_ENGINE_STRICT=1` (no silent C fallback); `AI_TEST_ENGINE=c` runs them on the C loop instead. Env scrubbers in test helpers keep `INFER_TOOL_SERVER`, `INFER_ENGINE`, `INFER_ENGINE_STRICT`.
- Root `conftest.py` isolates the run from the live model server and systemd (`tests/test_isolation_guard.py`): `INFER_BASE_URL` (env + scratch-HOME env file) = unroutable `http://127.0.0.1:9/v1/` (tests needing a server set their own), a no-op logging `systemctl` shim first on PATH, and in-process TCP connects to 127.0.0.1/localhost:8080/8081 are refused and recorded -- any recorded attempt fails the session (`AI_TEST_ALLOW_LIVE_PORTS=1` opts out). `os.kill`/`os.killpg` of a `llama-server`/`llama-proxy` process (group) the run did not start is refused and recorded too (fails the session; `AI_TEST_ALLOW_LIVE_KILL=1` opts out): ai-backend's `kill_llama_server()` SIGKILLs every llama-server on the host, so serve tests must stub it.
- `tests/conftest.py` also isolates per test: `AI_STATE_DB`, a dead `AI_EMBED_URL`, `INFER_TOOL_SERVER=0`, trader state paths, `INFER_LEARNING_AUTO_APPROVE=1`.
- Notable files: `test_build.py` (`make ci` / `-Werror` build in a temp copy), `test_engine_default.py` (default engine, deprecation notice, missing-agent fallback), `test_engine_parity.py`, `test_engine_interactive.py` (pty sessions), `test_config_templates.py` (templates hold no personal data; CI workflow shape), `test_evals_runner.py`.

Agent eval set (`evals/`): `evals/tasks/NN_<id>.json` are realistic CLI-assistant tasks (file edits, shell, multi-step tool use, recovering from a failing command, refusing a destructive script, ...). Each has `prompt`, optional `files`/`env`, `checks` (`answer_contains`, `file_exists`, `file_contains`, `tool_used`, `tool_result_contains`, `max_steps`; any check takes `"not": true`) and a `mock` script (`steps` of `{tool, args}`, a list = parallel calls; `final` = the task_complete summary). `python3 evals/run_evals.py --mock [--json out.json]` runs every task offline against `tests/mock_llm_server.py` (tools really run in a temp workdir with an isolated HOME; exit 1 on any failure). Against a model: `python3 evals/run_evals.py [--engine c|py] --base-url URL --model M --json out.json` (defaults to `INFER_*` / `~/.local/share/ai/env`; `--min-pass` sets the exit threshold, default 0; `--engine py` runs the `agent/` Python engine with `INFER_ENGINE_STRICT=1`). Progress: one line per task as it finishes (`[i/N] PASS id  steps=S  12.3s`). Timeouts: a task's `timeout`, else per tier on live runs (easy 300, medium 600, hard 1800 s; 60 with `--mock`), times `--timeout-scale`. A failed task keeps its temp dir (`result["kept"]`) with `stdout.txt`/`stderr.txt` (full), `session.json` and `debug/last_request.json` + `debug/last_response.raw` (via `INFER_DEBUG_DIR`); the progress line prints their paths (`result["artifacts"]`). In `--mock` mode answers and tool calls are scripted, so a task also fails when a scripted tool call returns an error unless the step has `"expect_error": true` (which must then really error); every task needs an observable check (`file_*`, possibly `"in": "home"`, or `tool_result_contains`). `tool_used` alone does not count.

CI (`.github/workflows/ci.yml`, ubuntu-latest): `test` × engine `[py, c]` (apt `libcurl4-openssl-dev libssl-dev`, pip `pytest requests google-api-python-client google-auth google-auth-oauthlib`, `make ci`, `AI_TEST_ENGINE=<engine> pytest tests/ -q`), `privacy` (`privacy_check.py --all` with `AI_PRIVATE_PATTERNS=/dev/null`, i.e. generic patterns only), `evals-mock` × engine (`make ci`, `run_evals.py --mock --engine <engine>`). The suite must not depend on this machine: no `zulip`, `rich`, `node`, local model, real `~/.config/ai` or `~/.local/bin/ai` on the runner (tests needing optional tools skip with a reason).

No linter or package manifest. For quick manual checks, run the binary directly (e.g. `INFER_* env vars set; echo "hi" | ./ai "say hello"`).

Required environment variables (the binary exits early without all three):
- `INFER_BASE_URL` — must end in `/v1/`; the C code appends `chat/completions`
- `INFER_API_KEY`
- `INFER_MODEL`
Optional environment variables:
- `INFER_AUTO_APPROVE=1` — auto-approve all `execute_command` calls without prompting.
- `INFER_DEBUG` — dump raw request/response payloads to stderr on every loop iteration.
- `INFER_QUIET=1` — suppress `[thinking]` output from the `think` tool (same as `-q`).
- `INFER_TOOL_CHOICE` — `required` (default) or `auto`; controls the `tool_choice` field sent in every request.
- `INFER_MAX_TOOL_OUTPUT` — caps individual tool output (default: 65536).
- `INFER_CONTEXT_WINDOW` — explicit model context in tokens (user-only; `ai-backend ctx` no longer writes it). Otherwise the per-slot `n_ctx` from `/props` (or `/v1/models`), capped by `LLAMA_CTX_SIZE` (the server's total `--ctx-size`, used alone only when nothing is detected). When known, `apply_context_budget` (C) / `Budget.apply` (agent/cli.py) derive trim/stub/tool-output limits from it in both directions: budget = n_ctx·3 − tool catalog − reply reserve (min(n_ctx/4, max(8192, max_tokens)) tokens); trim = 0.80·budget, stub = 0.95·budget, max_tool_output = clamp(budget/4, 4000, 256 KB). ≤32K windows get the old tightened values, long ones looser (128K ≈ 199K/236K/62K with the full catalog). Unknown window → defaults; explicitly set values always win. The effective cap is exported to tools as `INFER_EFFECTIVE_MAX_TOOL_OUTPUT` (read_file whole-file/digest thresholds and ranged-chunk size, web fetch limits). `INFER_PRINT_BUDGET=1` (or `INFER_DEBUG`) prints the values. Self-correction: a response whose `usage.prompt_tokens` > 80% of n_ctx forces a trim by the measured chars/token before the next request; an HTTP 400 "exceeds the available context size" trims to ~30% of trim_threshold and retries once. Tests: `tests/test_context_budget.py`.
- `INFER_STEP_MAX_TOKENS` — per-step completion cap (default 32768; an explicit `INFER_MAX_TOKENS` also sets it). Both engines send min(`INFER_MAX_TOKENS`, cap) as `max_tokens`. Python engine runaway guard (`agent/llm.py` `RunawayGuard`, wired in `Client.chat(guard=...)` / `Engine._request`): the stream is aborted (HTTP connection closed, so llama-server cancels the generation) when the estimated completion tokens (max(SSE text events, chars/4) over content + reasoning + tool arguments) exceed the cap, when reasoning exceeds 2x a configured reasoning budget, or on a repetition loop in PROSE only (content/reasoning outside a ``` fence; tool arguments and fenced code are exempt): the same 40-512-char unit repeated 8x back to back at the end, or the last 16 lines identical -- data-like lines/units (starting with `|`, or mostly digits/punctuation: CSV, matrices, tables) and tiny patterns (`-----`) excluded; the same checks also run on a digit-normalised copy (counter loops "item 17, item 18 ..."), there only for letter-heavy units; plus a recurrence check for drifting loops (reworded paragraphs, no exact unit back to back) over the last 16 KB of prose (`find_recurrence`, every 256 chars): a normalised line (lowercase, digits->0, >= 8 chars, >= 2 words, >= 4 letters; not data, indented, code-ending, fenced or a rule; short/single-token lines such as `**file.py**` or `Step 3` still count as lines, never as the recurring one; adjacent identical lines count once) recurring >= 6 times as true repeats while <= 40% of the lines from its first use on are unique, or >= 40 lines with <= 30% distinct -- except a template (the recurring lines evenly spaced with a unique line, the item's name, in every gap: an N-item report never trips). Counter (digit-normalised) loops count only for units of <= 2 lines (a numbered multi-line block is a template). Every repetition trip carries `first` / `cut` (where the loop's first pass begins / ends). A content-only reply (no tool call by trip time) is SALVAGED when the text before `first` is a real answer (>= 200 chars with a complete paragraph) and the kept text does not end with ':': content truncated at `cut`, the turn finishes like `finish_reason: stop`, a one-line notice and a `generation_guard` metrics row with `action: salvaged`. Anything less ("Let me check each file." + loop) gets the abort/nudge/retry below. On abort: the partial reply is dropped, a user nudge appended (repetition: "...got stuck repeating itself..."; caps: "...ran past the per-step token limit... write large files in parts") and the request retried once with presence_penalty >= 1.5 and reasoning_effort low; a second abort appends a `[GENERATION ABORTED]` user message and ends the step (3 such steps in a row stop the task). Each abort is a one-line stderr notice and a `generation_guard` row in `~/.cache/ai/metrics.jsonl`. `INFER_REPETITION_GUARD=0` disables the loop detector (the caps stay). Both engines: on `finish_reason: "length"` the last tool call of the reply (and any earlier one whose arguments are not valid JSON as-is) is NOT executed -- it gets a tool error "cut off at the token limit and was NOT executed" (the JSON repair would otherwise write a truncated file). Tests: `tests/test_generation_guard.py` (recorded Ornith final-answer loop in `tests/fixtures/ornith_final_answer_loop.tokens`, replayed via the `MOCK_RUNAWAY_SEQ` item key `chunks_file`; mock `MOCK_RUNAWAY_SEQ` / `MOCK_DISCONNECTS`, `MOCK_TOOL_SEQ` item `{"calls": [...], "finish_reason": "length"}`).
- `INFER_FREQ_PENALTY` / `INFER_PRESENCE_PENALTY` — per-request penalties (defaults 0.10 / 0.05, sent when > 0; they override the server's own `--presence-penalty`). The Python engine, with no `INFER_*` value, sends a non-neutral server-profile value (`LLAMA_FREQUENCY_PENALTY` / `LLAMA_PRESENCE_PENALTY` > 0) instead of its default; the C loop keeps its defaults.
- Sampling profiles (`ai-backend`): `use` (via `apply_model_path`) applies the model family's recipe to the env file -- gguf arch `qwen35`/`qwen35moe` (Qwen3.6/3.8, Ornith; file-name fallback when the header can't be read) gets `qwen35-thinking`: INFER_TEMPERATURE 1.0, INFER_TOP_P 0.95, INFER_TOP_K 20, INFER_MIN_P 0.0, INFER_PRESENCE_PENALTY 1.5, LLAMA_PRESENCE_PENALTY 1.5; unknown models are left as is. Ownership sidecar `~/.local/share/ai/profile.json` (`written` = what the profile last wrote, `previous` = value before it took the key, `disabled`): a key is written only when absent, still equal to what the profile wrote, already equal to the target, or (no record) holding ai-backend's neutral default (LLAMA_*_PENALTY 0.0 / repeat 1.0, which write_env always writes); anything else is user-owned and never touched. `profile off` restores `previous` for keys still holding the profile's value and disables auto-apply; `profile apply` re-enables; `profile show` lists each key's owner. A malformed sidecar is treated as empty. `ai-backend mode <preset>` writes presence_penalty 1.5 to both INFER_ and LLAMA_ keys, so mode and profile agree. Tests: `tests/test_ai_backend_profiles.py`.
- `INFER_TOOL_PROFILE=core` — send only the core tool subset (~10 KB instead of ~45 KB). Set automatically for windows ≤32k tokens and `--short-ctx`.
- `INFER_KEEP_REASONING` — reasoning retention (default `2`; `all` = send every past step's reasoning, the pre-2026-10 behaviour; `0` = none). When each request is built, `reasoning_content` and inline `<think>…</think>` (plus anything before an unmatched `</think>`) are stripped from assistant messages outside the recent window of the current turn (the assistant messages after the latest real user message; harness nudges, `[User note mid-task` and `Here is the image file` are not turn boundaries). `INFER_KEEP_REASONING_BLOCK` (default `4`; `0` = strict sliding window) adds hysteresis: the kept count grows from N to N+B-1, then the oldest B are stripped at once (`stripped_in_turn`), so the request prefix -- and llama.cpp's prompt cache -- breaks once every B steps instead of on every step (8-step chain at N=2: 1 break with B=4, 5 with B=0). A stripped reasoning-only reply (no tool_calls) is sent with content `""`, never null. Only the request is stripped: the in-memory history and the saved session (`-r`, debugging) keep all reasoning while the history stays under the trim budget. Stripping is a pure, monotonic function of the history: a stripped message stays stripped. Trim/stub/auto-compact/`:compact`/`:status` sizes measure the request, not the history. Without an explicit value `--preserve-thinking` / `INFER_PRESERVE_THINKING` means `all`. Python: `aitools/sessions.py` `request_view` (via `agent/messages.py`, `Engine._wire`); C: `reasoning_request_view` in `ai.c` (cJSON, same rules; its `reasoning_internal_prefixes[]` must equal `RETENTION_INTERNAL_PREFIXES`, a test asserts set equality; with `INFER_DEBUG` a history that does not parse is reported and sent unstripped). Tests: `tests/test_reasoning_retention.py` (mock `MOCK_TOOL_SEQ` item `{"calls": [...], "reasoning": "...", "content": "..."}`; golden `tests/golden/reasoning_chain_all.json` = requests before the feature, reproduced by `all`).
- `INFER_TRIM_THRESHOLD` — triggers message trimming if context exceeds this size (default: 100000). Trimming only runs above it, cuts to ~60%, always keeps the system prompt and first/latest real user turns, keeps assistant `tool_calls` with their tool replies, and first strips old reasoning (the `INFER_KEEP_REASONING` window without the hysteresis block -- this changes the history, so the saved session loses that reasoning; never with `all`), then shortens old tool output, then drops messages. `trim-messages <file> <max_bytes> [keep]` takes the keep value as an optional 3rd argument (ai.c passes its effective setting).
- `INFER_STUB_THRESHOLD` — stubs subsequent tool results once context size exceeds this (default: 250000).
- `INFER_ENGINE` — unset/empty/`py` (default): the Python engine (`agent/`) behind the C binary as terminal front-end (see "Architecture"). `c`: the legacy C loop in `ai.c`, deprecated and kept for one release; it prints a one-line deprecation notice on stderr (never stdout). `INFER_ENGINE_PATH` overrides where the `agent/` dir is looked up; a missing `agent/` falls back to the C loop with a warning, unless `INFER_ENGINE_STRICT=1` (then exit 1; tests and `evals --engine` set it).
- `INFER_TOOL_SERVER=0` — never use the persistent tool server (see "Tool server"); every list-tools/call-tool/render-markdown goes through `popen` as before. Default on. `INFER_TOOL_SERVER_SCOPE=0` skips the systemd-run scope when spawning it. Test helpers that scrub `INFER_*` keep `INFER_TOOL_SERVER` (tests/conftest.py sets it to 0).
- `INFER_RESUME=1` — resume the previous conversation (same as `-r`/`--resume`). See "Session persistence" below.
- `INFER_SYSTEM_PROMPT_FILE` — path to a system-prompt override file. Defaults to `~/.config/ai/system_prompt.md` if that exists; otherwise the compiled-in `SYSTEM_PROMPT` is used. Lets you tune agent behavior without recompiling.
- `INFER_AUTO_COMMIT=1` — opt into git auto-commit after successful commands (same as `--git`; `--no-git` wins). Off by default; it only stages files git already tracks (`git add -u`) and restores the index if the commit is blocked.
- `INFER_SERVER_WAIT` — seconds both engines keep retrying a LOCAL model server that refuses connections (default 30: one still starting up), then print one line `[ai] cannot reach the model server at <url> (...); is it running? Check \`ai-backend status\`.` and exit 1 (non-interactive).
- `INFER_IDLE_TIMEOUT` (old name `INFER_FIRST_BYTE_TIMEOUT`, still honoured; the new one wins) — a streaming chat request that receives no byte for this many seconds is abandoned, never retried (default 300; `0` = off). llama.cpp sends nothing during prompt processing, so streaming requests to a local server carry `"return_progress": true` (`INFER_RETURN_PROGRESS=auto|1|0`; auto = localhost/127.0.0.1 only, hosted APIs may reject unknown fields) and the `prompt_progress` chunks (role-only deltas, ignored by both SSE parsers) keep the stream alive during a long prefill. For servers that ignore it the FIRST byte may take max(idle, ~prompt tokens (payload bytes/4) / `INFER_PREFILL_TPS` (default 300)). Python: socket timeout in `Client._post` (allowance until the response starts, then the idle value); C: `CURLOPT_LOW_SPEED_LIMIT/TIME` = that max for the whole request. Exit 1 with a one-line error naming `INFER_IDLE_TIMEOUT` and `ai-backend status`. A 503 whose body has `"type": "backend_unavailable"` (llama-proxy: the backend failed to start) is not retried either: its message (the reason, e.g. the VRAM preflight error) is printed on one line; other 502/503/504 keep their 3 retries. 5xx failures also exit 1. Tests: `tests/test_server_failfast.py` (mock `MOCK_HTTP_ERROR`, `MOCK_STALL`).
- `INFER_DEBUG_DIR` — every chat request overwrites `<dir>/last_request.json` (payload) and `<dir>/last_response.raw` (raw response bytes, flushed as they arrive, so a killed stall keeps the partial stream). Both engines; `evals/run_evals.py` sets it per task.
- `INFER_FETCH_BASIC=1` — force `fetch_webpage` to use the plain urllib+trafilatura path instead of the default robust `fetch_smart` cascade (curl_cffi TLS impersonation → Playwright+stealth → urllib).
- `INFER_RECALL_K` — auto-recall size: at most this many relevant items `state-export memory --query` ADDS after the unchanged memory render (default 6; `0` = no recall block). Relevance gate for vector hits: `INFER_SEARCH_MIN_SIM` (absolute cosine floor, default 0.68) and `INFER_SEARCH_DELTA` (keep within this of the best hit, default 0.08); the explicit `search_memory` tool uses a looser gate: `INFER_SEARCH_TOOL_MIN_SIM` (absolute floor only, default 0.62, no FTS-agreement rule). `INFER_EMBED_AUTODRAIN` (read by the tool server from its own environment; default on there, `0` = never drain the embed queue when idle).
- `AI_EMBED_URL` (default `http://127.0.0.1:8091`), `AI_EMBED_MODEL` (GGUF path), `AI_EMBED_BIN` (llama-server path) — the local embedder (see "Semantic memory").
- `INFER_LEARNING_AUTO_APPROVE=1` — store new self-improvement lessons as `approved` immediately (default `0`: they are `proposed` and need `ai lessons approve|review`). Only approved, unexpired lessons reach the system prompt.

## Architecture

```
ai (C, one process per run; child subreaper)
 │  terminal: line editor + history, raw keys (ESC, Shift-Tab, Ctrl-O, :btw), /dev/tty approvals, boxes/spinner
 ├─ default ── fork python3 agent/ --frontend-fd 3 ── newline JSON events (agent/protocol.py)
 │              Python engine: agent loop, LLM HTTP/SSE, aitools IN-PROCESS
 │              (native tools forked per call, MCP tools on an in-process McpPool)
 └─ INFER_ENGINE=c (deprecated) ── C loop in ai.c ── ai_toolclient.c ── tool server (`ai_mcp.py serve`,
                                    pooled MCP sessions) ── else popen `python3 ai_mcp.py call-tool …`
aitools/ ── state.db (memory, lessons queue, ledger, scheduled tasks, sessions, chat audit, vectors)
         ── ai-embed (optional local embedder; `ai-backend embed …`) for semantic memory
zulip_ai_bridge.py ── runs `ai` per Zulip message;  trader/ ── deployed separately (see "Trader")
```

Both engines implement the same loop (whole-request parity is pinned by `tests/test_engine_parity.py`); the bullets below describe it with the C names, `agent/` mirrors them.

**The agent loop** (`agent/loop.py`; legacy `ai.c`). Owns the conversation. Responsibilities:
- C engine only: builds the `messages` JSON by hand with `snprintf`/`json_escape` and parses responses with the vendored **jsmn** tokenizer (token-index walking, not a DOM; most C response-handling bugs live there).
- Runs the agentic loop: POST via libcurl → parse `tool_calls` → execute each → append `tool` messages → repeat (capped at **30** iterations per turn). Sends `tool_choice: required` by default (overridable via `INFER_TOOL_CHOICE=auto` for servers that do not support it).
- Handles `think`, `task_complete`, `execute_command` and `present_plan` **natively** (not via aitools dispatch):
  - `think`: prints `[thinking] …` to stdout (suppressed by quiet mode); returns `{"ok":true}`.
  - `task_complete`: renders the `summary` argument via `render-markdown`, logs the job, and exits the loop.
  - `execute_command`: opens `/dev/tty` for a `[Y/n]` confirmation prompt (bypassed when `g_auto_approve` is set), runs the command with `2>&1` capture, and wraps the result in `[Command Success]` / `[Command Failed with exit status N]`.
- Delegates every **other** tool call to `aitools`: in-process in the Python engine; in the C engine through the persistent tool server when it answers (`ai_toolclient.c`, see "Tool server"), else `python3 ai_mcp.py call-tool <server> <tool> <json-args>` (likewise `list-tools`, `render-markdown`).
- Assembles the system prompt from: hardcoded `SYSTEM_PROMPT`, live system context (`get_system_context`), persistent memory, and loaded skills.
- Caps each tool result to `INFER_MAX_TOOL_OUTPUT` (default: 64 KB) and stubs any result once `messages_json` exceeds `INFER_STUB_THRESHOLD` (default: 250 KB) to prevent context blowup. Trims messages when context exceeds `INFER_TRIM_THRESHOLD` (default: 100 KB).
- Detects pipe-writer via `/proc` inspection and includes the originating command name in the user message.
- Handles image file arguments: detects `.png`/`.jpg`/`.jpeg`/`.webp` paths, base64-encodes them, and injects a `image_url` content block into the first user message.
- Intercepts `[IMAGE_DATA_SUCCESS:<path>]` returned by `read_file` and similarly injects the image into conversation context.
- Detects `finish_reason: "length"` (model hit token limit) and injects a recovery nudge instead of rendering truncated output.
- In interactive mode handles colon-commands (`:compact`, `:clear`, `:status`, `:memory`, `:auto`, `:mode`, `:help`, …) and Shift-Tab (`ESC [ Z`), which cycles the permission mode (manual / plan / auto) at the prompt and during a task.
- The interactive prompt is the C line editor (`read_line_interactive` / `lineed_*` in `ai.c`, used by both engines): history (up/down), cursor keys, Ctrl+A/E/K/U/W/L, Home/End, Delete; history persists in `~/.cache/ai/input_history`. Terminal writes go through `lineed_write` (retries EINTR/partial writes; a dead tty ends the session like EOF).
- `:compact` trims the conversation towards a target size with the same protocol-safe rules as automatic trimming; it does NOT ask the LLM for a summary.
- **Session persistence:** at the end of every run the full `messages_json` is written to `~/.cache/ai/sessions/last.json`. `-r`/`--resume` (or `INFER_RESUME=1`) reloads it: the engine runs `session-transcript` on it, which converts the raw array into a clean user/assistant transcript (JSONL, one message per line) — old system message, tool churn, and internal nudges are dropped, and `task_complete` summaries become assistant text. Each line is spliced in via `append_message` between the fresh system message and the new user turn, avoiding dangling-tool_call API errors.
- **System prompt** is assembled from `load_system_prompt()` (file override → compiled-in `SYSTEM_PROMPT` fallback) plus live context, memory, and skills.

**`ai_mcp.py` / `aitools/` — the tool backend (Python).** `ai_mcp.py` is a ~30-line shim: it puts the directory of its realpath (a checkout) and then `~/.local/share/ai/lib` (where `install.sh` copies the package) on `sys.path`, runs `aitools.cli.main()` as a script, and makes `import ai_mcp` return `aitools.compat` — a flat namespace re-exporting every name of the old single-file module; rebinding a name on it (`monkeypatch.setattr(ai_mcp, "MEMORY_PATH", …)`) is forwarded to every submodule holding that object (same trick as `trader/legacy.py`). Subcommands matching how `ai.c` calls it: `list-tools`, `call-tool`, `render-markdown`, `trim-messages`, `session-transcript`, `run-scheduler`. Module map:
  - `cli.py` — subcommand `main(argv) -> int`; `call-tool` = parse/repair JSON → `registry.prepare` → metrics tee → `registry.invoke`.
  - `registry.py` — `TOOL_SCHEMAS` (native catalog, list-tools order, from `schemas_part1/2.py`), `HANDLERS` (tool name → `h_<tool>(args) -> str`; a call matches on tool name **or** server name, first entry wins, else the MCP server), `prepare` (alias normalisation, required/type checks), `invoke`, `dispatch(server, tool, args) -> str` (exactly what `call-tool` prints), `repair_json`, `CORE_TOOL_PROFILE`.
  - `handlers.py` (tool handlers), `calendar_tools.py` (gcal_* handlers), `web.py` (search + fetch cascade), `files.py` (read/write/edit/patch/list/search_files, PDF), `shell.py` (execute_command, playgrounds, background processes), `state.py` (the SQLite state store + legacy migration, see "Runtime state"), `memory.py` (save_memory, FTS memories, vault, context pool), `history.py` (history index cache, Zulip chat-log tools), `sessions.py` (trim-messages, session-transcript, sessions index), `scheduler.py` (schedule_task, reminders, run-scheduler loop), `selfimprove.py` (skills, failure ledger, lessons, recap), `metrics.py` (log_metric, `classify_tool_output`), `mcp_client.py` (load_config, stdio JSON-RPC client, `McpPool` of persistent sessions), `server.py` (the persistent tool server, `ai_mcp.py serve`), `render.py`, `browser.py` (browser daemon, computer_control), `research.py` (arXiv/PubMed), `misc.py`.
  - Golden guards: `tests/test_aitools_layout.py` (list-tools bytes, call-tool outputs, shim < 80 lines, modules ≤ 1500 lines, install layout).

It:
- Defines the native tools as OpenAI function schemas (`registry.TOOL_SCHEMAS`; `think` first, `task_complete` last), plus every MCP server's tools.
- Implements the actual logic for each (DuckDuckGo Lite scraping, HTML→text, PDF extraction via pdftotext/pypdf/pdfplumber fallback chain, binary-file heuristic rejection, etc.). `edit_file`: search-and-replace on an existing file. Falls back to a trailing-whitespace-tolerant fuzzy match if the exact string is not found.
- **Web fetching:** the public `fetch_webpage` tool (and `parallel_fetch`, and the search auto-fetch of the top result) route through `fetch_smart` — a cascade of curl_cffi TLS impersonation → Playwright+stealth → plain urllib (`fetch_webpage_basic`). `fetch_webpage_basic` is the plain rung and the only thing `fetch_smart` falls back to (never the public `fetch_webpage`, which would recurse). `INFER_FETCH_BASIC=1` forces the plain path.
- Acts as a generic **MCP client**: any server in `mcp.json` is started over stdio JSON-RPC and its tools are namespaced `<server>__<tool>`. `ai.c` splits on `__` to route calls back.
- **Google Calendar** (`gcal.py`, lazily imported by the handlers in `aitools/calendar_tools.py`): `gcal_list_events`, `gcal_check_availability`, `gcal_quick_add` (natural-language event via Google's parser), `gcal_create_event`, `gcal_update_event` (patch semantics), `gcal_delete_event`.   - `zulip_bridge/` module map: `config` (env file, zuliprc, `resolve_ai_bin`), `owner` (owner detection), `files` (`FileParser`), `text` (`clean_response`), `runner` (`run_ai_subprocess`, `extract_session_fallback`), `memory` (`ZulipMemoryManager`), `context` (`ContextWindowManager`), `handler` (`MessageHandlerMixin`: `_process_message`, `handle_message`), `bridge` (`ZulipAiBridge`), `cli` (`run_check`, `main`). - Calendar/Zulip logic is unit-tested offline in `tests/test_integrations.py` by mocking the Google service object / Zulip client and asserting on the request bodies built.

### Tool server

Used by the legacy C engine only (the Python engine runs aitools in-process). `python3 ai_mcp.py serve [--idle-exit 900] [--drain-idle 20] [--drain-limit 16]` (`aitools/server.py`) is a per-user daemon that answers the binary's list-tools / call-tool / render-markdown requests without starting an interpreter per call (10 `read_file` calls through the binary: ~0.05 s vs ~0.48 s). `ai_toolclient.c` (`toolclient_call(op, server, tool, args, timeout, &out)`) is used by `ai.c`'s `list_tools_json`, `tool_server_call_tool` and `render_markdown`; only a failure where nothing can have run (no connection; a failed send, since the final newline never left; a reset before any answer byte, which on AF_UNIX means our request sat unread in a dying server's queue; or a pre-execution refusal `stale|mismatch|unsupported|bad request`) falls back (after one respawn attempt) to the old popen path. Once the request (one buffer, request + newline; the server ignores an unterminated line) was delivered, a lost connection or unusable answer is `TOOLCLIENT_LOST`: the model gets `Error: tool server connection lost; the tool may or may not have run — check before retrying.` and nothing is re-run. `execute_command`, `think`, `task_complete` stay native in C.
- No-resend invariants (comments in `tc_exchange` and `server._Handler.handle`): one request per connection; the client writes nothing after the request's newline; the server consumes the whole line (readline, no size limit) before dispatching, and never runs an unterminated line; Linux AF_UNIX semantics (a server that closes with our request unread resets the connection, one that read it gives EOF). Break any of these and "reset before any answer byte ⇒ never ran" no longer holds.
- Socket `$XDG_RUNTIME_DIR/ai/tools.sock` (else `~/.cache/ai/tools.sock`), dir 0700, socket 0600, other uids dropped (SO_PEERCRED, checked by both ends); pid file `~/.cache/ai/tools.pid`; server stderr in `server.log` next to the socket. Newline-delimited JSON: `{"id","op":"hello|list_tools|call|render|shutdown","server","tool","args" (raw model JSON text, repaired like call-tool),"text","timeout","cwd","env" (the caller's whole environment),"script"}` -> `{"id","ok","result","error","exit","stderr"}` (+`version`, `pid` for hello).
- Spawn: when `systemd-run` is on PATH and a systemd user instance is reachable (`$XDG_RUNTIME_DIR/bus` or `systemd/private`), via `systemd-run --user --scope --collect --quiet --unit=ai-tools-<uid>-<ts>-<pid> -- python3 <ai_mcp.py> serve`, so the server does not die with the spawning unit's cgroup (zulip bridge restart, oneshot end); if that does not come up, or otherwise, the client double-forks + setsid `python3 <ai_mcp.py> serve` (stdio /dev/null, cwd /, ai's child-subreaper flag dropped meanwhile so the daemon is not ai's child), waits up to 2 s for the socket, retries once; at most 3 spawns per process, none after a failed one. Concurrent spawns are serialised by `tools.sock.lock` (a live server makes a newcomer exit).
- Staleness is server-side: the server fingerprints `aitools/*.py` (mtime+size) at start and on every request; a change, or a caller whose `script` resolves to another aitools package, gets `{"ok":false,"error":"stale"}`: the server unlinks its socket at once, finishes in-flight calls and exits; the client respawns once and retries. A caller with another `HOME` gets `"mismatch"` (popen fallback, no respawn).
- Execution: native tools, list_tools and render run in a child FORKED from the pre-imported server (chdir to the caller's cwd, `os.environ` = caller's env, fd 1/2 on pipes, `os._exit`), so output bytes equal `call-tool`'s (guarded by `tests/golden/cli_cases.json`), cwd-relative tools are correct under concurrency, raise/print/`sys.exit` stay inside the call, and a timeout (`timeout`, default 120 s = `INFER_COMMAND_TIMEOUT`) SIGKILLs the call's process tree -> `ok:false,"timeout"`; the client then appends the same `[SYSTEM WARNING: Command timed out ...]` the popen path gives and does not re-run it. A client hang-up (ESC) kills the call. Metrics are logged by the server (`metrics.record_tool_metric`, skipped when the caller has `INFER_PRIVATE_MODE`).
- MCP tools run in the server on `mcp_client.McpPool`: one stdio session per server name (reader thread routing JSON-RPC ids), restarted on EOF, timeout (min(timeout, 60 s)) or config change; a replaced session with calls in flight is retired and closed by its last caller; starting a session holds only that server name's lock; `"disabled": true` servers are never started; a call is retried on a fresh session only when the request could not be written (`McpSendError`), never after the server received it. MCP config is resolved with the caller's cwd/env (`load_config(cwd, environ)`).
- Idle: after `--drain-idle` s without requests (and `INFER_EMBED_AUTODRAIN` != 0 in the LATEST request's env; the drain also takes `AI_STATE_DB`/`AI_EMBED_*`/HOME/PATH from it, never from the spawner's env; no drain before the first request) a forked child runs `search.backfill_locked(limit, queued_only=True)`; exits after `--idle-exit` s idle, when its socket is removed/replaced, or on SIGTERM.
- Tests: `tests/test_tool_server.py` (isolated HOME + private `XDG_RUNTIME_DIR`; fake MCP `tests/fixtures/fake_mcp.py`); `tests/conftest.py` sets `INFER_TOOL_SERVER=0` for every other test.

### Python engine and the C front-end (default)

`agent/` is a port of the `ai.c` loop (`loop.py` Engine: setup, tasks, guards, colon-commands; `cli.py` argv/env → Config; `llm.py` payload + SSE incl. fragmented tool-call deltas, retries, `/props` probe; `messages.py` system prompt/user turn/trim; `tools.py` catalog + dispatch; `native.py` think/task_complete/execute_command/present_plan/git; `session.py` save/resume/history/pipe writer; `protocol.py` IPC; `prompt_text.py` = `SYSTEM_PROMPT`, kept byte-identical to ai.c by a test). Unless `INFER_ENGINE=c`, `main()` (after the `-v/-s/deep-research/lessons/metrics/-h` early exits and `load_env_file`) calls `frontend_main()` (`ai_frontend.c`): it forks `python3 <dir of ai>/agent` (else `~/.local/share/ai/lib/agent`, installed by `install.sh`) with `--frontend-fd 3 <all args>` and fd 3 = a socketpair end, then only renders events and handles the terminal: line editor + history, raw-mode keys during a task (ESC → `interrupt`, Shift-Tab → `set permission_mode`, Ctrl-O, `:btw`), `/dev/tty` approval prompts (`approve` → `approve_reply`), the spinner, tool/think/answer boxes (`print_*` from ai.c via `frontend_ui_t`). No HTTP/LLM code runs in C in this mode. Ctrl-C: the front-end SIGTERMs the engine, which kills its command/tool processes. Protocol (newline JSON): see the `agent/protocol.py` docstring. The engine never writes fd 1 itself (`sys.stdout` → stderr); every intentional byte goes through `out`/`err`/`final` events so the front-end is the only writer.
- Child reaping: `ai` is a child subreaper (`prctl` in `main`), so `nohup … &` jobs left by commands are reparented to it. `reap_children()` (`ai_reap.h`, in `ai_terminal.c`) collects them with `waitpid(-1, WNOHANG)` only at safe points (each line-editor tick, each front-end event-loop tick; never while a `popen`/`system` child of ours is outstanding). The engine pid is registered with `reap_track()` so its status is kept for the front-end's exit handling; a no-op `SIGCHLD` handler (`SA_RESTART`) just wakes `poll`.
- Tools: native handlers run like the tool server runs them (`aitools.server.run_forked` + `_child_invoke`: forked from the pre-imported engine, cwd/env of the engine, fd 1/2 captured, tree killed on `INFER_COMMAND_TIMEOUT` or ESC); MCP tools on an in-process `McpPool` (never re-sent after delivery); metrics via `aitools.metrics.record_tool_metric`. The C engine's tool server is not used.
- Memory recall: the system prompt's memory section is recomputed for every interactive user turn; everything else in the system message is frozen at session start, as in C.
- Intentional differences from the C loop: `[IMAGE_DATA_SUCCESS:…]` is detected on the raw tool output (C checks the decorated text, so its intercept never fires); the `[HARD STOP]` message is valid JSON (C's literal is malformed); HTTP ≥400 responses are reported instead of being parsed as an empty stream; `remote_exec` uses the Python handler (no libremote_harness session); interactive input is not cut at 4095 chars; `-r <file>.json` also accepts an existing path.
- Tests: `tests/test_engine_parity.py` (6 scripted conversations, whole requests + ANSI-stripped stdout equal), `tests/test_engine_interactive.py` (pty: turns, colon-commands, ESC, Ctrl-C, approvals, orphan reaping), `tests/test_engine_default.py`, `tests/test_agent_unit.py`. `tests/test_tool_server.py` pins `INFER_ENGINE=c`.

### Adding or changing a tool

A native tool needs, kept in sync:
1. Its OpenAI function schema in `aitools/schemas_part2.py`, before the final `task_complete` entry (list position = `list-tools` order; then re-capture `tests/golden/list_tools*.json` with `AITOOLS_REGEN_GOLDEN=1`).
2. A handler `h_<tool>(arguments) -> str` (in `aitools/handlers.py` or the domain module) registered in `registry.HANDLERS`; add required args to `TOOL_REQUIRED_ARGS` if any.
3. Usually nothing in `ai.c` or `agent/` — both route any non-native tool to aitools automatically. Tools needing native handling (`think`, `task_complete`, `execute_command`, `present_plan`, the `[IMAGE_DATA_SUCCESS:...]` sentinel) live in BOTH `ai.c` and `agent/loop.py` + `agent/native.py`.

`think` and `task_complete` have Python fallback handlers in `registry.HANDLERS` (safety net if an engine's routing misses them), but their real handling is in the engines.

### Cross-process contracts (easy to break silently)

- Image flow: `read_file` on an image returns the literal string `[IMAGE_DATA_SUCCESS:<abspath>]`; the engine detects this prefix and injects a base64 `image_url` user message.
- Command results are `$ <cmd>\n<output>`, or `$ <cmd> — failed (exit N)\n<output>\n[SYSTEM WARNING: Command failed…]` (both engines); `failed (exit` / `[SYSTEM WARNING:` mark the result as an error for hints, the state log and the self-improvement ledger.
- `delegate_task` recursively spawns the `ai` binary itself (`/usr/local/bin/ai` or `./ai`) with a 60s timeout.
- Both files resolve `ai_mcp.py` / `ai` from `./` first, then `/usr/local/bin/` — so the local dev copy shadows the installed one when run from the repo.

## Skills

Both engines auto-load `SKILL.md` files into the system prompt from `./.agents/skills/*/` (per-project) and `~/.config/ai/skills/*/` (global). These are plain markdown guidance for the model, not executable. The `.agents/skills/` dir in this repo is the project's own skill set (e.g. `karpathy_guidelines`, `autonomous_troubleshooting`).

## Semantic memory

- **Embedder** (`aitools/embed.py`): EmbeddingGemma-2 (`~/.local/share/ai/models/embedding/embeddinggemma-2-UD-Q4_K_XL.gguf`) on a SEPARATE CPU-only llama.cpp build (`~/.local/share/ai/llama.cpp-embed`; the main llama.cpp build/server is never touched): `llama-server --embeddings --pooling mean -c 8192 -ub 8192 -b 8192 --host 127.0.0.1 --port 8091 -t min(12,nproc/2) -np 4 -ngl 0`, `CUDA_VISIBLE_DEVICES=`. `./install.sh embed` (opt-in; the default install only prints a hint) installs `ai-backend`, clones+builds it (`-DGGML_CUDA=OFF -DLLAMA_CURL=OFF`, target `llama-server` only; a dir without `CMakeLists.txt` from an interrupted clone is removed and re-cloned) and downloads the model when missing, and installs `services/ai-embed.service` (not enabled; `Nice=10`, `ExecStart=ai-backend embed serve`). `ai-backend embed status|start|stop|serve [--dry-run]`. `embed.embed(texts, "query"|"document") -> vectors | None` never raises; a query has a 0.5 s total budget. Prefixes: `task: search result | query: …` / `title: … | text: …`.
- **Storage** (state db): `vectors(item_type, item_id, model, dim, v128, v768, updated, hash, source_ts)`, little-endian float16 blobs, each L2-normalised at its dim (128-d Matryoshka prefix + full 768-d); a document longer than 2000 chars is up to 4 chunks `<id>`, `<id>#1`, …; `hash` = sha1(model, title, chunk) decides re-embedding. `item_fts` (FTS5, rowid = id*4+{memory 1, lesson 2, chat 3}) and `embed_queue(item_type, item_id, enqueued, attempts)` are maintained by SQLite TRIGGERS on `memory`/`lessons`/`chat_audit` (any writer, raw SQL included; deletes also drop the vectors via a PK range `item_id >= id||'#' AND < id||'$'`; triggers are dropped and recreated on every schema upgrade); `remember`/`vault_write` queue notes in Python. Item types: `memory`, `lesson` (only approved+unexpired surface), `chat`, `history_chunk` (rows of the history_index.db cache), `note` (`r<rowid>` remember rows, `v:<title>` vault notes).
- **Indexing:** `ai_mcp.py embed-backfill [--limit N] [--queued-only] [--quiet]` (`search.index_items`, serialised by `<state db>.embed.lock`) drains the queue and (without `--queued-only`) scans every source: embeds new/changed chunks (8 per request), copies vectors of identical chunks, removes vectors of vanished items; exit 2 when the embedder is down. A batch that fails while `/health` is ok is retried item by item; each failure bumps `embed_queue.attempts` and an item at 3 is skipped (logged on stderr) until its content changes. Queue rows are deleted only if processed and enqueued before the run started. The tool server drains it (`--queued-only` path, bounded batch) when idle; `ai` itself never starts it.
- **Search** (`aitools/search.py`): `search_memory(query, sources=None, since=None, k=8) -> [dict(item_type, item_id, text, score, source_ts, match)]` = RRF (k=60) of FTS5 BM25 (item_fts, memories, vault_fts, history_fts; query = OR of content words, stopwords and tokens < 3 chars dropped) and vectors (cosine on v128 over all candidates, top 50 reranked on v768, best chunk per document) gated by cos >= max(0.68, best - 0.08); a vector hit below 0.73 counts only when FTS found the same item. Nothing passes = no results. Pure stdlib (`struct`, `math.sumprod`); numpy only above 20k vectors. FTS-only when the embedder is down. Read-only (no write lock). Tool `search_memory(query, sources?, since?, k?)` (core profile too); `since` = ISO date, epoch or `7d`/`12h`/`2w`.
- **Auto-recall (additive):** `ai.c` (`read_memory_for_prompt` in `ai_session.c`) runs `state-export memory --query '<request, ≤1000 bytes, single-quoted>'` (stdin text when the prompt is only the pipe placeholder; no request, or a failed/empty subprocess = plain `state-export memory`). Output (`search.memory_section`): the UNCHANGED `memory_render()` (all memory up to 4 KB, as before), then, only if something passes the relevance gate, a block of ≤ 1.5 KB: `Pinned (beyond the memory budget):` pinned lines the render could not fit, and `Recalled for this request …` up to `INFER_RECALL_K` items from chats/history/lessons/notes plus memories beyond the 4 KB budget, as `- [source YYYY-MM-DD] text` (≤ 300 chars each). Recall is skipped (render only) when off, the embedder is down, or nothing is embedded yet. The Python engine recomputes it for every interactive turn. Measured: +~45 ms startup with ~6.5k vectors (query embedding ~12 ms).
- Tests: `tests/test_semantic_search.py` with `tests/fixtures/fake_embedder.py` (deterministic hashed bag-of-word-stems vectors with an EmbeddingGemma-like score distribution: cos = 0.55 + 0.45 * overlap; inputs containing `POISON` get HTTP 500); `tests/conftest.py` points `AI_EMBED_URL` at a dead port and sets `INFER_EMBED_AUTODRAIN=0` for every test. Retrieval eval: `python3 evals/run_evals.py --retrieval [--fake] [--embed-url URL] [--json out]` over `evals/retrieval/pairs.json` (48 synthetic query→item pairs) reports R@1/R@5/MRR, hybrid vs FTS-only; real embedder when it answers `/health`, else the fake one.

## Learning queue

`aitools/learning.py`: lessons go `proposed` -> `approved` (60-day expiry for every approved lesson, auto-approved and migrated ones included; each recurrence of the same kind+tool+signature bumps `hits` and extends it; a recurrence after expiry re-queues the lesson as `proposed`) or `rejected`; `expired` after `expires`. Read paths filter by expiry in the query (no startup writes); `ai lessons list|review|approve|reject|prune` (ai.c execs `ai_mcp.py lessons ...` only for no subcommand or list/review/approve/reject/prune; `ai lessons learned X` is a normal prompt) manages them. `prune` expires and deletes rejected lessons older than 30 days.

## Runtime state locations

- `~/.cache/ai/history.jsonl` — every job logged (prompt, pipe writer, response).
- `~/.local/share/ai/state.db` (`$AI_STATE_DB` overrides) — the single SQLite state store (`aitools/state.py`; WAL, `busy_timeout=5000`, writes in `BEGIN IMMEDIATE` with lock retries and rollback on a failed COMMIT, so the Zulip bridge, scheduler daemons and `ai` can write concurrently). Opening never takes the write lock once the schema exists. Read paths (`connect(read=True)`: state-export, renders, lists) wait at most 1 s for any lock and open an unwritable db via a `mode=ro` URI; the startup subcommands `ai.c` runs synchronously (`state-export`, `session-recap`, `lessons-for`, `rag-memories`) cap all lock waits at 1.5 s (`state.lock_budget`). Tables: `meta` (`schema_version=3`, `migrated_v1`, `migration_report`, `chat_audit_pruned_at`), `memory` (persistent memory; `pinned` column = core memories; reaches the system prompt via `ai_mcp.py state-export memory [--query <request>]`, read once per `ai` process, see "Semantic memory"; `save_memory` dedupes case-insensitively and evicts the oldest whole lines past 4000 chars; `memory_render` caps at 4096 bytes keeping the newest), `lessons` (PITFALL/FIX/MASTER/NOTE; `UNIQUE(kind, tool, signature)`, `status` default `approved`, `hits`, `expires`; rendered as the old lessons.md markdown blocks), `ledger` (failure/recovery rows, args stored only as a hash, capped at 5000 rows), `sessions` (index of saved conversations, updated as the history indexer sees session files), `scheduled_tasks` (task spec JSON + `next_run`; the row IS the task, deleting it cancels; only `<id>.pid` lock files stay in `~/.config/ai/scheduled_tasks/`; `ai.c` shows the countdown via `state-export tasks`), `chat_audit` (one row per Zulip exchange, rows older than 90 days deleted on open at most once a day), plus FTS5 `memories` (remember/recall) and `vault_fts` (vault note index), and for semantic memory `vectors`, `embed_queue` and FTS5 `item_fts` (see below). Guard/timeout errors are not learned from. CLI: `ai_mcp.py state-export memory [--query Q]|lessons|tasks`, `state-migrate [--retry] [HOME]`, `state-stats`, `embed-backfill [--limit N]`.
- **Legacy migration:** the first `state.connect()` of a process on the default path (no `$AI_STATE_DB`) imports `~/.config/ai/memory.txt` (latin-1 bytes tolerated), `memory.db` (its FTS tables), `self_improve/lessons.md` (hand edits tolerated) and `ledger.jsonl` (corrupt lines skipped), `scheduled_tasks/*.json`, and `~/.local/share/ai/zulip_chats.jsonl` + `~/.cache/ai/zulip_chats.jsonl`, in one transaction that sets `meta.migrated_v1`; then each original is renamed `*.migrated.bak` (nothing is deleted). Live old-code scheduler daemons are replaced. Per-source state is kept in `meta.migrated:<source>` / `meta.migrate_failed:<source>`: a source that fails is rolled back alone, left in place, and only re-attempted by `ai_mcp.py state-migrate --retry`. After the first pass, every process's first connect stats the legacy paths, and a file that exists again (lines written by a still-running old-code process) is imported and renamed again (`.migrated.bak.N`). That re-import is idempotent for the append-only tables: imported `ledger`/`chat_audit` rows carry `import_key` (sha256 over every non-id column, UNIQUE index) and the importers `INSERT OR IGNORE` (skips counted as `ledger_duplicates`/`chat_audit_duplicates`), so a restored legacy file adds 0 rows; live appends keep a NULL key and are never merged. The v3->v4 upgrade keys every existing row and deletes exact duplicates (lowest id kept; triggers drop their `item_fts`/vector rows). Tests: `tests/test_state_dedupe.py`. Errors are counted in `meta.migration_report` and never break startup. The scheduler daemon backs off exponentially (1 s doubling to 300 s, one log line per step) while the db is unusable. With `$AI_STATE_DB` set there is no lazy migration; `tests/conftest.py` sets it per test, so tests never touch the real HOME.
- `~/.local/share/ai/history_index.db` — NOT state: a derived, rebuildable FTS cache over `history.jsonl` and the session files (`rebuild_history_index`).
- `~/.config/ai/trader.json` — Robinhood account mapping (`{"accounts": {"agentic": ..., "primary": ..., "roth": ...}}`); env `RH_*_ACCOUNT` overrides. Trading refuses if the agentic account can't be resolved.
- `~/.config/ai/mcp.json` — MCP server registry (`aitools/mcp_client.py: load_config`). Search order, first non-empty file wins: `$INFER_MCP_CONFIG`, `~/.config/ai/mcp.json`, `~/.config/ai/mcp_config.json`, `./mcp.json`, `./mcp_config.json` (cwd; dev only, gitignored), `~/.gemini/config/mcp_config.json`, `~/.lmstudio/mcp.json`. Entries with `"disabled": true` are skipped.

### Config templates (`config/`)

Personal config is not tracked. `config/*.example*` are the templates: `mcp.example.json` (robinhood, zulip, pubmed entries, all `"disabled": true`, no secrets; pubmed reads `PUBMED_SEARCH_URL`/`PUBMED_API_KEY` from the env), `trader.example.json` (`<..._ACCOUNT>` placeholders, which `RobinhoodExecutor.configured_account` treats as unset, also in `RH_*_ACCOUNT`), `private_patterns.example.txt` (comments only), `zuliprc.example` (format reference only; not seeded; a key containing `REPLACE_WITH` is reported as "not configured" by `zulip_ai_bridge.py --check` and `zulip_mcp_server.py`). `install.sh` copies each of the others to `~/.config/ai/<name without .example>` (mode 600) **only when the target is missing**; it never overwrites. When it seeds `~/.config/ai/mcp.json` it prints a notice: **MCP servers ship disabled (robinhood included); enable one by setting `"disabled": false` in `~/.config/ai/mcp.json`**. A seeded `~/.config/ai/mcp.json` takes precedence over `./mcp.json` and the legacy paths, so a server configured only in a cwd `mcp.json` stops loading once it exists. Templates use placeholders / example.com only; `tests/test_config_templates.py` enforces that.

## Trader

`trader/` (shim `robinhood_trader.py`; see `docs/robinhood_trader.md`) is NOT run from the working tree. `bash trader/deploy.sh [--ref <commit>]` builds `~/.local/share/ai-trader/releases/<ts>-<sha>/` from a committed tree (default HEAD, refused when the tree is dirty; `--ref <commit>` deploys that commit via `git archive` whatever the worktree state). The test gate runs ALL trader test files (`TRADER_TESTS` in the script; `tests/test_trader_deploy.py` checks every `tests/test_trader_*.py` is listed) against a temporary `--shared` clone checked out at the deployed commit, never the worktree; a failure refuses the deploy. It then atomically repoints `~/.local/share/ai-trader/current`, which `services/robinhood-trader.service` runs; it never touches systemd (restart the service yourself). `AI_TRADER_HOME` overrides the base dir (tests use a temp one). Never place/cancel real orders or call the real broker MCP from tests.

## Privacy (the GitHub repo is public)

- Never commit personal data: lab data files, account numbers, private hosts/IPs, real e-mails, `/home/<user>` paths. Put such values in `~/.local/share/ai/env`, `~/.config/ai/*.json`, or a gitignored file.
- `.githooks/pre-commit` runs `scripts/privacy_check.py` on every commit (enabled by `install.sh` via `git config core.hooksPath .githooks`). It checks generic leak patterns plus a personal denylist in `~/.config/ai/private_patterns.txt` (outside the repo, one regex per line). `python3 scripts/privacy_check.py --all` audits every tracked file. Mark an intentional line with `privacy-ok`.
- Machine/lab-specific skills stay local and gitignored (e.g. `.agents/skills/boltzgen-ops/`, `.agents/skills/*_private/`); `install.sh` still syncs them to `~/.config/ai/skills/`.
- Tests run the binary with `cwd` set to a temp dir or with auto-commit off — never let the binary commit inside this repo.
